# 실결제(PG)·법무 확인 항목

> 이 문서는 **출시 전 반드시 확인해야 하는 것**과, **현재 코드가 실제로 하는 일/하지 않는 일**을 구분해 정리합니다.
> 현재 결제는 전부 테스트 환경(`MockPgProvider`)이며 실제 카드 승인·송금이 발생하지 않습니다.

## A. 실결제 도입 전 사업자 확인 11항목

| # | 확인 항목 | 확인할 내용 | 현재 코드 |
| --- | --- | --- | --- |
| 1 | 디지털 상품·개발 용역 취급 가능 여부 | PG 약관상 소프트웨어 라이선스·용역 취급 제한 | 미확인(테스트) |
| 2 | 다수 판매자 입점 구조 지원 | 마켓형 정산(분리 정산·지급 대행) 지원 여부 | 미확인(테스트) |
| 3 | 지원 결제수단 | 카드·계좌이체·가상계좌·간편결제 목록 | 4종 가상 구현 |
| 4 | 대금 보호·정산 구조 | 에스크로 계약 여부, 정산 주기, 지급 주체 | 미확인(모의 보류) |
| 5 | 최대 보류 기간 | 검수 기간(최대 14일)을 보류할 수 있는지 | 미확인 |
| 6 | 구매확정·자동확정 방식 | 자동확정 일수, 연장 가능 여부 | 결제수단별 3~14일 가정 |
| 7 | 분쟁 시 지급 중지 범위 | 주문 단위 중지 가능 여부 | 요청·결과만 기록 |
| 8 | 부분 환불 가능 조건 | 수단별 부분 취소 지원 | 계좌이체·가상계좌 미지원 가정 |
| 9 | 단계별 결제 지원 | 다건 결제·부분 결제 지원 | 단계별 별도 주문으로 구현 |
| 10 | 판매자 확인 절차 | KYC·사업자 검증 API 제공 여부 | 수동 심사만 |
| 11 | 기지급 거래 환불 처리 | 지급 후 환불 회수 절차 | `RECOVERY_REQUIRED` 로 분리 구현 |

**원칙**: 확인한 기능만 활성화하고, 지원하지 않는 기능은 대체 절차 또는 "미지원"으로 화면에 표시해야 합니다.
현재 UI는 이 원칙에 따라 대금 보호를 "모의 보류(테스트)"로, 부분 환불 미지원 수단을 "미지원"으로 표시합니다.

## B. 전자상거래법 관련 확인

1. **청약철회 제한(제17조 제2항)** — 디지털 콘텐츠는 "다운로드 시작" 시 청약철회 제한 가능.
   - 필요 조치: 결제 전 명시적 동의, 동의 사실(시각·IP·문구 버전) 증빙 보관
   - 코드: `startPayment` 에서 동의 필수, `ConsentLog`(kind `WITHDRAWAL_LIMIT`, version, ip, textHash) + `Order.consentWithdrawalAt/consentIp` 기록
   - **법률 확인 필요**: 문구가 "다운로드 시작 전" 고지로 충분한지, 상품별로 예외(설치형)를 둘지
2. **청약철회 제한 예외** — 표시·광고와 다르거나 계약과 다르게 이행된 경우 제한 불가. → 분쟁·환불 절차 필수
3. **표시·광고** — "100% 안전", "무조건 환불", "모든 권리 검증 완료" 등 미보장 표현 금지(코드 전체에서 미사용)
4. **사업자 정보 표시** — 상호·대표·사업자번호·주소·연락처 (푸터에 표시, 실제 값으로 교체 필요)
5. **개인정보** — 수집·이용 동의, 위탁(호스팅·결제), 파기 정책, 정산계좌 암호화
6. **전자금융거래법** — 플랫폼이 판매자 대금을 보관·지급하는 구조는 PG의 "지급대행" 계약 또는 전자지급결제대행 등록
   검토가 필요할 수 있음 → **반드시 법률 검토**
7. **세무** — 사업자 판매자 세금계산서 발행(플랫폼 수수료 포함), 개인 판매자 3.3% 원천징수, 부가세 처리
8. **소프트웨어 라이선스** — 재배포·수정 범위, 제3자 오픈소스 고지 의무
9. **지식재산권 양도** — 특허·상표 이전 등록 절차, 공동 권리자 동의, 기존 이용허락 승계

## C. 결제 연동 시 구현해야 할 것

- [ ] PG 선택 및 계약(마켓형 정산 지원 여부 확인)
- [ ] `PgProvider` 구현체 작성 (`createPayment`, `getPayment`, `refundPayment`, `requestPayout`, `getPayout`)
- [ ] 웹훅 서명 검증 규격 적용 (현재 HMAC-SHA256 예시)
- [ ] 결제창/리다이렉트 흐름 연결 (현재 `/pay/[paymentId]` 는 샌드박스)
- [ ] 결제수단별 자동확정 일수·부분환불 지원 여부를 실제 정책으로 설정
- [ ] 에스크로/보류 API 연동 여부 결정 → 미지원이면 `NOT_SUPPORTED` 표시
- [ ] 대사 API 연동 (일일 정산 파일 vs 내부 원장)
- [ ] 실패·타임아웃 재시도 정책 확정
- [ ] PCI-DSS 범위 확인 (카드정보 직접 저장 금지 — 현재 저장하지 않음)

## D. 법무 검토가 필요한 문서

| 문서 | 현재 상태 | 검토 포인트 |
| --- | --- | --- |
| 이용약관 | 초안 (`/legal/terms`) | 플랫폼 책임 범위, 판매자 의무, 분쟁 처리 조항 |
| 개인정보처리방침 | 초안 (`/legal/privacy`) | 수집 항목·보유 기간·위탁·국외이전 |
| 청약철회·환불 정책 | 초안 (`/legal/withdrawal`) | 디지털 콘텐츠 제한 요건, 부분 환불 |
| 맞춤 개발 계약서 | 초안 (`Contract.draftNotice`) | 도급/용역 구분, 권리 귀속, 하자보수, 지체상금 |
| 지식재산권 양도 계약 | 미작성(상담 후 개별) | 양도 범위, 기존 허락 승계, 등록 이전 |
| 판매자 입점 계약 | 미작성 | 수수료, 정산, 제재, 책임 분담 |

## E. 보안·운영 확인

- [ ] `VAULT_MASTER_KEY` KMS 관리, 회전 절차
- [ ] 악성코드 검사 벤더 도입(현재 패턴 검사만)
- [ ] 사용자 업로드 코드 실행이 필요하면 격리 컨테이너(네트워크·시간·메모리 제한)
- [ ] 관리자 2차 인증(현재 미구현 — 코드에 요구사항으로만 존재)
- [ ] 접속 로그·감사 로그 보존 기간(전자상거래법 5년 등)
- [ ] 백업 암호화 및 복구 리허설
- [ ] 개인정보 파기 자동화

## F. 현재 구현과 요구사항의 차이(정직한 표기)

| 요구 | 구현 상태 |
| --- | --- |
| 실제 결제·대금 보호 | ❌ 테스트 PG 모의 처리 |
| 파일 악성코드 검사 | ❌ 패턴 검사만 |
| 본인인증·계좌 실명확인 | ❌ 없음(수동 확인 전제) |
| 원격 삭제·프로그램 비활성화 | ❌ 구현하지 않음(정책상 금지) |
| AI 최종 판단 | ❌ 차단, 참고 의견만 |
| 메일·SMS 알림 | ❌ 인앱 알림만 |
| 기업 구매 승인 워크플로 | ⚠️ 승인 한도 검사만, 결재선은 없음 |
| 유지보수 계약 자동 과금 | ❌ 데이터·알림만 |
