# 1. 거래 유형별 자금·납품 흐름

이음마켓의 안전거래는 서로 다른 세 가지를 합친 것이다. 화면과 문서에서 이 셋을 섞어 부르지 않는다.

| 영역 | 누가 실제로 수행하는가 | 플랫폼이 하는 일 | 하지 않는 말 |
| --- | --- | --- | --- |
| ① 결제대금 보호 | 계약한 결제 사업자(PG) | 사업자 기능을 호출하고 결과를 그대로 표시 | DB의 정산 상태를 "보류"로 바꾼 것을 대금 보호(에스크로)라고 부르지 않는다 |
| ② 납품물 보관 | 플랫폼 비공개 저장소 | 암호화 보관, 주문별 접근 권한, 버전 고정, 접근 기록 | 전문 소스코드 에스크로 계약과 같은 서비스라고 하지 않는다 |
| ③ 검수 후 판매자 정산 | 플랫폼이 판단, 사업자가 지급 | 납품·검수·분쟁·잔액을 확인한 뒤 지급 요청 | 지급 요청 접수를 지급 완료라고 하지 않는다 |

## 공통 원칙

- 돈의 상태는 **내부 기록**과 **사업자에 조회한 결과** 두 벌로 관리하고, 대사 작업이 둘을 비교한다.
- 웹훅과 브라우저의 결제 성공 화면은 "조회해 보라"는 신호일 뿐이다. 결제 완료는 서버가 사업자에 직접 조회해 금액까지 맞을 때만 인정한다.
- 납품물 접근은 결제 확인 직후 열린다. 구매확정을 먼저 눌러야 파일을 받는 구조는 없다.
- 다운로드와 구매확정은 별개다. 다운로드 기록은 증빙일 뿐, 검수 완료의 근거가 아니다.
- 구매 시점의 설명·파일 버전·권리 조건·수수료는 주문에 복사해 고정한다(DB 트리거로 변경 차단).

## A. 완성형 프로그램 사용권 / B. 소스코드 구매

두 유형은 흐름이 같고 **받는 권리**가 다르다. A는 사용권, B는 소스 파일과 정해진 이용 범위(수정·상업적 이용·재배포·재판매)다. 어느 쪽도 지식재산권이 이전되지 않는다(`licenses.ip_transfer` 는 DB에서 항상 false).

```
판매자                     플랫폼                               결제 사업자            구매자
  │ 납품 파일 사전 등록 ─▶ 암호화 보관·해시·검사·심사
  │                        판매 시작(파일 버전 공개 = 잠금)
  │                                                                                  상품·조건 확인
  │                        보호 기간 검증(검수일+1 ≤ 보류 가능일) ◀──────────────── 결제 요청
  │                        주문 생성(조건 스냅샷) ──────────────▶ 결제창 ◀───────── 결제
  │                        ◀── 웹훅(서명 검증, 중복 제거) ────── 승인
  │                        서버 조회로 금액·상태 확인 ─────────▶
  │                        [돈] 결제 확인, 대금 보호 상태 기록
  │                        [납품물] 파일 존재·해시 확인 후 접근 허용 ─────────────▶ 다운로드(만료 링크)
  │                        검수 기간 시작(접근이 열린 시점부터)                      설치·검수
  │                        ◀──────────────────────────────────────────────────────── 구매확정 또는 문제 제기
  │                        정산 조건 확인(결제·납품·검수·분쟁·환불·판매자·잔액·중복)
  │                        지급 요청(멱등성 키) ───────────────▶ 접수
  │ ◀──────────────────────────────────────────────────────────── 지급
  │                        지급 완료 확인 후 원장 기록·정산 완료
```

갈림길:

- **파일 전달 실패**(저장소 장애, 해시 불일치): 납품 상태 `failed`, 검수 기간은 시작하지 않는다. 복구 작업이 다시 확인하고, 열리는 시점부터 검수 기간을 센다.
- **문제 제기**: 내부 정산을 막고(`blocked`), 사업자에 지급 보류를 요청한 뒤 그 결과(`confirmed`/`unsupported`/`failed`)를 분쟁에 따로 기록한다.
- **환불**: 요청 → 운영자 결정 → 사업자 결제 취소 → 취소 성공 확인 후에만 `completed`. 전액 환불이면 추가 다운로드를 막고, 이미 받은 파일은 회수할 수 없다는 점을 양측에 안내한다. 원격 삭제·비활성화 기능은 만들지 않는다.
- **이미 지급된 뒤의 문제 제기·환불**: 보류로 되돌릴 수 없으므로 `post_settlement_review`(사후 환불·회수 검토)로 보낸다.
- **검수 지연**: 기한 알림 → 판매자가 검수 종료 심사 요청 → 운영자가 근거를 남기고 종료. 자동확정은 사업자 정책과 검토된 운영 정책이 일치할 때만 켠다.
- **설치 지원 포함 상품**: 계약에 적은 설치 완료 조건(`products.install_done_criteria`)을 검수 체크리스트에 포함한다.

## C. 맞춤 개발 (단계별)

국내 PG의 대금 보호는 무형 디지털 상품·장기 용역에 제약이 있으므로, 전체 금액을 한 번에 묶어 두지 않고 **단계마다 별도 주문·결제**를 만든다. 사업자가 지원하지 않는 임의 분할 지급은 구현하지 않는다.

```
의뢰 등록 → 견적 제안 → 계약 버전 합의(양측 동의 시 잠금)
  └─ 단계 n: 조건 확정 → 해당 단계 주문·결제 → [결제 확인 후] 작업 시작
             → 납품 제출(파일 보관) → 필수 파일 확인 → 접근 허용 → 검수
             → 승인 / 수정 요청(범위 내) / 변경 계약(범위 밖) → 정산 조건 확인 → 지급
```

- 각 단계 주문도 위 7대 상태를 그대로 쓴다(`orders.order_type = 'milestone'`).
- 납품 제출(`submitted`)과 접근 허용(`granted`)을 구분한다. 화면 캡처·시연 영상만으로는 `granted` 가 되지 않는다. 최종 단계는 소스·실행 방법·계약상 필수 문서가 있어야 한다(`milestones.required_files`).
- 추가 요구는 변경 계약으로 관리한다. 기존 범위와 추가 범위를 나란히 적고, 금액·기간 변경에 양측이 동의하면 새 계약 버전이 생긴다.
- 사업자가 단계별 결제를 지원하는지는 기능 확인표의 `staged_payments` 로 관리한다. 미확인이면 실결제에서 맞춤 개발 결제를 열지 않는다.

## D. 지식재산권 거래

```
상담 → 비밀유지 조건 동의(본문 해시 기록) → 자료실 열람 승인 → 권리·기술 확인
  → 거래 조건 확정 → 계약(법률 검토 전에는 '초안' 표시) 및 결제 → 자산 인도 목록별 인수 확인
  → 권리 이전 절차 확인 → 완료·정산
```

- 공개 소개와 비공개 자료실을 분리한다. 자료실은 승인받은 사람만 열람하고 열람 기록을 남긴다.
- 독점 거래는 계약·결제 진행 중 `ip_listings.locked_by_deal_id` 로 잠가 중복 판매를 막는다.
- 서비스 계정·앱 등록 자산은 제공자의 공식 이전 절차 증빙이 있어야 인수 확인이 된다(DB 제약). 비밀번호 전달만으로는 완료되지 않는다.
- 고액·권리 양도 거래는 분쟁이 없어도 별도 확인 절차(`extra_verification`)를 선택할 수 있다.
- 금액이 크고 기간이 길어 일반 결제 보호 범위를 넘을 수 있다. 사업자가 지원하지 않으면 "대금 보호 미지원 거래"로 표시하고 계약서 기반 절차로 안내한다.

## 실결제 도입 전 기능 확인표

`provider_capabilities` 테이블에 사업자별로 기록한다. `confirmed` 인 기능만 켠다. 그 외에는 대체 절차를 안내하거나 미지원으로 표시한다.

| 키 | 확인할 내용 | 미확인·미지원일 때 |
| --- | --- | --- |
| `digital_goods` | 디지털 상품·개발 용역 취급 가능 여부 | 실결제 차단 |
| `multi_seller` | 다수 판매자 입점(지급대행·서브몰) 지원 | 실결제 차단 |
| `methods` | 지원 결제수단 | 확인된 수단만 노출 |
| `escrow_structure` | 대금 보호·정산 구조 | 주문에 "대금 보호 미지원" 표시 |
| `max_hold_days` | 최대 보류 기간 | 검수일+1 을 넘는 상품은 결제 차단 |
| `auto_confirm` | 구매확정·자동확정 방식과 일수 | 검수 기간과 충돌하면 결제 차단, 플랫폼 자동확정 꺼 둠 |
| `dispute_hold` | 분쟁 시 지급 중지 가능 범위 | 내부 보류만 적용하고 그렇게 표시 |
| `partial_refund:<수단>` | 부분 환불 가능 조건 | 전액 환불 후 재결제 또는 합의 종결 안내 |
| `staged_payments` | 단계별 결제 지원 | 맞춤 개발 결제 미개방 |
| `seller_kyc` | 판매자 확인 절차 | 판매자 지급 차단 |
| `post_payout_refund` | 이미 지급한 거래의 환불 처리 방식 | 사후 환불·회수 검토(수동) |

실제 연동과 샌드박스의 구분, 미구현 항목은 `docs/05-연동-현황과-미구현.md` 에 있다.
