# 운영 및 장애 복구 매뉴얼

## 구성
| 프로세스 | ROLE | 하는 일 | 확장 |
|---|---|---|---|
| API | `api` | REST·SSE, 기동 시 `alembic upgrade head` | 수평 확장 가능 |
| 파이프라인 워커 | `worker` | 조사·대본·생성(외부 API 대기 위주), 큐 `pipeline` | `WORKER_CONCURRENCY` |
| 렌더링 워커 | `render` | FFmpeg 렌더·품질검수·패키지, 큐 `render` | CPU 수만큼. 기본 동시 1 |
| beat | `beat` | 60초마다 복구·예약 시작·성과 수집 | **1개만** |
| 웹 | – | Next.js | – |

- 서비스를 여러 컨테이너·서버로 나누면 **`STORAGE_BACKEND=s3`** 가 필요합니다(워커끼리 파일 공유). docker compose 는 공유 볼륨을 씁니다.
- 작은 규모는 `TASK_MODE=inline` 으로 API 1개만 띄워도 동작합니다(백그라운드 스레드 + 내장 주기 작업). 이 경우 렌더링이 API와 CPU를 나눠 씁니다.
- `ENCRYPTION_KEY` 를 잃거나 바꾸면 저장된 API 키·OAuth 토큰을 복호화할 수 없습니다. 반드시 백업하세요(키 보관 창고).

## Railway 배포
같은 저장소에서 서비스 5개를 만듭니다. `backend/` 를 루트로 하는 서비스 4개(ROLE=api/worker/render/beat)와 `frontend/` 1개, 그리고 PostgreSQL·Redis.
공통 변수: `DATABASE_URL`, `REDIS_URL`, `TASK_MODE=celery`, `SECRET_KEY`, `ENCRYPTION_KEY`, `STORAGE_BACKEND=s3`, `S3_*`.
API: `PUBLIC_BASE_URL`(API 공개 주소), `FRONTEND_URL`, `CORS_ORIGINS`(웹 주소). 웹: 빌드 변수 `NEXT_PUBLIC_API_URL`.
Render 는 `render.yaml` 블루프린트를 사용합니다.

## 상태 흐름
`PENDING → RESEARCHING → SCRIPTING → STORYBOARDING → GENERATING → EDITING → RENDERING → REVIEWING → COMPLETED`
그 외 `FAILED`, `CANCELLED`, `AWAITING_APPROVAL`.

## 장애 상황별 동작
| 상황 | 자동 동작 | 운영자 조치 |
|---|---|---|
| 워커·서버가 작업 중 종료 | 잠금이 15분(`LOCK_TTL_SECONDS`) 뒤 만료 → beat 가 60초 안에 다시 큐에 넣음. 완료 단계는 건너뜀 | 없음. 급하면 진행 화면에서 중지 후 다시 시도 |
| 생성 요청 제출 직후 종료 | `provider_requests` 에 남은 외부 `request_id` 로 **재제출 없이** 상태만 다시 조회 | 없음 |
| 같은 작업이 두 워커에 전달 | DB 잠금(`locked_by`)으로 한쪽은 즉시 `locked` 반환 | 없음 |
| 외부 API 5xx·타임아웃 | 지수 백오프+지터로 재시도, 429 는 Retry-After 준수. 제출은 같은 Idempotency-Key | 반복되면 관리자 → 실패·장애 탭에서 오류율 확인 |
| 영상 생성 실패·검수 거부 | 대체 모델 1회 → 그래도 실패하면 그 장면만 이미지 애니메이션으로 대체 | 필요 시 편집기에서 장면 재생성 |
| API 잔액 부족(403) | 과금 없이 `FAILED`, 안내 문구 표시 | 충전 후 "다시 시도" |
| 예산 초과 예상 | 과금 전에 `AWAITING_APPROVAL` | 사용자가 승인 |
| 품질 미달 | 문제 장면만 재생성(기본 최대 2회, 예산 안에서) | 관리자 → 품질·한도·정책에서 기준 조정 |
| YouTube 쿼터 초과 | 수집을 줄이거나 건너뛰고 계속 진행 | 다음 날 자동 회복 |

## 점검
- 관리자 → 운영 현황: DB·Redis·워커 큐·FFmpeg·디스크 여유.
- 관리자 → 실패·장애: 공급자별 7일 오류율·평균 처리 시간, 실패 로그.
- 헬스체크: `GET /api/healthz`.

## 백업·복구
- PostgreSQL: `pg_dump` 정기 백업. 복구 뒤 진행 중이던 작업은 beat 가 이어서 실행합니다.
- 저장소: 버킷 버전 관리 또는 복제. Higgsfield 원본은 7일 뒤 사라지므로 자체 저장소가 유일한 사본입니다.
- 마이그레이션: 모델 변경 후 `alembic revision --autogenerate -m "..."` → 검토 → 배포(기동 시 자동 적용). 되돌리기 `alembic downgrade -1`.

## 비용 통제 지점
1. 제작 전 최대 예상 비용 산정(재생성 여유 25% 포함) → 한도 초과 시 정지
2. 유료 호출 직전마다 프로젝트·일·월 한도 재확인
3. 멱등 키로 중복 호출 차단, 완료 결과 재사용
4. 장면 단위 재제작
금액은 단가표 기준 계산값입니다. 공급자 응답에 청구액이 없으므로 월 1회 콘솔 청구액과 대조하세요.
