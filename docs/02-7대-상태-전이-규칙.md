# 2. 7대 핵심 상태와 전이 규칙

구현: `src/domain/states.ts`(순수 함수), `src/server/trade.ts`(주문 행을 잠그고 적용) · DB 불변식: `prisma/migrations/0001_init/migration.sql` · 검증: `test/states.test.ts`, `test/schema.test.ts`, `test/integration.test.ts`

주문 하나에 상태 컬럼이 7개 있다. 한 컬럼은 한 가지만 말한다.

| 컬럼 | 값 | 누가 바꾸는가 |
| --- | --- | --- |
| `payment_status` 결제 | unpaid → pending → paid → partially_refunded / cancelled, failed | 서버가 사업자에 조회한 결과 |
| `escrow_status` 대금 보호 | none → test_simulated / held / unsupported → dispute_hold → released / refunded | 사업자에서 실제로 일어난 일만 |
| `delivery_status` 납품 | not_ready → (submitted) → granted / failed → revoked | 파일 확인 작업, 환불 완료 |
| `inspection_status` 검수 | not_started → in_progress ↔ revision_requested → confirmed / auto_confirmed / closed_by_admin, disputed | 구매자, 운영자, 자동확정 작업 |
| `dispute_status` 분쟁 | none → open → resolved (→ open 재접수) | 당사자 접수, 사람 운영자 결정 |
| `refund_status` 환불 | none → requested → processing → completed / failed, post_settlement_review | 운영자 결정, 사업자 취소 확인 |
| `payout_status` 판매자 지급 | not_eligible → eligible → requested → paid, unknown, failed, blocked, void | 정산 작업, 사업자 지급 확인 |

`test_simulated` 는 테스트 결제 시뮬레이터에서만 쓰며, 화면에는 "테스트 — 실제 대금 보호 아님"으로 표시한다. 전체 허용 전이표는 `TRANSITIONS` 상수에 있다.

## 이벤트별 규칙

서비스는 주문 행을 잠근 트랜잭션 안에서 `reduce(상태, 이벤트)` 를 호출하고 결과를 저장한다. 사업자 호출은 트랜잭션 밖에서 한다. 같은 이벤트가 다시 와도 결과가 같다.

| 이벤트 | 조건 | 결과 |
| --- | --- | --- |
| 결제 확인 | 조회 금액 = 주문 금액 | 결제 paid, 대금 보호 기록, 접근 기한 설정. 금액이 다르면 failed |
| 결제 확인(취소로 조회됨) | 승인보다 취소 통지가 먼저 온 경우 포함 | 결제 cancelled, 납품을 열지 않음 |
| 납품 확인 | 결제 paid, 약속한 파일 종류 존재, 주문 시점 해시와 동일, 저장소에서 읽힘 | 납품 granted, **이때** 검수 시작과 기한 설정. 문제가 있으면 failed 이고 검수는 시작하지 않음 |
| 구매확정 | 구매자 본인, 납품 granted, 분쟁 없음 | 검수 confirmed, 지급 eligible |
| 자동확정 | 운영 정책 켜짐 + 사업자 정책 일치 + 기한 경과 + 분쟁 없음 | 검수 auto_confirmed, 지급 eligible |
| 검수 종료(운영자) | 고객지원·최고관리자, 근거 기록, 납품 granted | 검수 closed_by_admin, 지급 eligible |
| 문제 제기 | 당사자, 결제된 주문 | 분쟁 open, 지급 blocked, 검수 disputed. 이미 지급이 진행됐으면 사후 검토 표시만 |
| 외부 보류 결과 | 분쟁 open | confirmed 일 때만 대금 보호 dispute_hold. 그 외에는 안내만 남김 |
| 분쟁 결정 | 사람 운영자(고객지원·최고관리자), 근거 필수, AI 단독 결정 금지 | 환불 requested / 거래 재개 / 정산 진행 / 외부 절차 안내 |
| 환불 시작 | 금액 범위 내, 진행 중 환불 없음, 부분 환불이면 결제수단이 지원 | 환불 processing, 지급 blocked. 지급이 먼저 잡혔으면 post_settlement_review |
| 환불 확인 | 사업자의 취소 성공 확인 | 환불 completed. 전액이면 결제 cancelled, 납품 revoked, 지급 void |
| 지급 요청 | 아래 지급 전 확인 전부 통과 | 지급 requested(접수) |
| 지급 타임아웃 | — | 지급 unknown. 같은 멱등성 키로 조회한 뒤에만 재시도 |
| 지급 조회 | paid / accepted / failed / none | paid, requested, failed, 또는 같은 키로 재요청 |

## 지급 전 확인 (`payoutBlockers`)

결제 완료, 사업자 결제 상태와 내부 기록 일치, 납품 완료, 검수 종료, 분쟁 없음, 환불 진행 없음, 판매자 승인·계좌 확인, 미지급(중복 아님), 실제 지급 가능 잔액. 하나라도 걸리면 사유를 모두 돌려준다.

## 환불과 지급의 경쟁

둘 다 같은 주문 행을 잠그고 서로의 상태를 본다. 먼저 잠근 쪽이 이긴다.

- 환불이 먼저: 환불 processing → 지급 요청은 "환불이 진행 중"으로 거절
- 지급이 먼저: 지급 requested → 환불은 post_settlement_review 로만 진행
- 추가 방어: `payouts.order_id` 유일, 환불·지급 멱등성 키 유일, 원장 `ref` 유일

`test/integration.test.ts` 의 ⑨번 테스트가 환불과 지급을 동시에 실행해 둘 중 하나만 사업자에 도달하는지 확인한다. 내장 Postgres(PGlite)는 트랜잭션을 한 줄로 세워 실행하므로, 실제 PostgreSQL 서버의 행 잠금 경합은 출시 전 부하 테스트로 한 번 더 확인해야 한다.

## DB가 스스로 막는 것

- 결제 확인 없이 납품 접근 허용, 납품 없이 검수 시작, 분쟁 중 지급 대상, 검수 미종료 지급 대상, 환불액 > 결제액
- 공개된 파일 버전의 파일 추가·교체·삭제(검사 결과 갱신만 가능), 빈 파일 등록
- 주문의 납품 버전·스냅샷·금액·수수료 변경, 동의가 끝난 계약 버전 변경
- 원장·감사 로그·다운로드 기록·대금 보호 기록의 수정·삭제
- 사업자 확인 없는 환불 완료·지급 완료 처리, 근거·처리자 없는 분쟁 결정

## 접근 규칙

- 주문 열람: 구매자·판매자·운영자. 정산 내역: 판매자 본인과 정산·최고관리자.
- 다운로드: 구매자 본인, 결제 확인, 납품 granted, 보관 기간 이내. 판매자 탈퇴 여부는 조건이 아니다.
