# 운영자 매뉴얼

운영자 콘솔: `/admin` (권한: 심사 `OPERATOR_REVIEW`, 고객지원 `OPERATOR_SUPPORT`, 정산 `OPERATOR_SETTLEMENT`, 최고관리자 `SUPER_ADMIN`)

## 0. 원칙

1. **상태를 섞지 않는다.** 결제/대금보호/납품/검수/분쟁/환불/정산은 각각 독립 상태다. 하나가 완료됐다고 다른 상태를 함께 바꾸지 않는다.
2. **일어나지 않은 일을 표시하지 않는다.** 내부 DB만 바꾼 것을 "대금 보호 완료"로 표현하지 않는다. 테스트 PG는 항상 "모의"로 표시된다.
3. **모든 판단은 근거·처리자·일시를 남긴다.** 분쟁 판단, 환불 처리, 상품 차단, 판매자 중지는 감사 로그에 자동 기록된다.
4. **AI는 최종 판단자가 아니다.** 분쟁 참고 의견만 제공하며 `decideDispute` 는 AI 주체를 거부한다.

## 1. 상품·파일 심사 (`/admin/products`)

확인 순서:
1. 납품물 개수와 검사 상태 — `ISSUE_FOUND`(문제 발견) 또는 빈 파일이면 **승인 불가**
2. 설명과 포함/제외 범위, 제3자 라이선스·외부 비용 고지 여부
3. 검수 기간(1일 이상)과 환불 정책 문구
4. 가격·사용권 조건(기간/영구, 사용자 수)

처리:
- **판매 승인** → 즉시 마켓 노출
- **차단**(BLOCKED) → 판매 불가, 사유 메모 기록
- **판매 중지**(SUSPENDED) → 기존 주문은 유지, 신규 판매만 중단

> 파일 해시는 "같은 파일인지"만 확인한다. 악성코드 검사·기능 검증이 아니다. 코드 실행이 필요하면 운영 서버와
> 분리된 일회성 격리 환경에서 수행하고, 결과를 별도 기록한다.

## 2. 판매자 심사 (`/admin/sellers`)

- 사업자: 상호·사업자등록번호·세금계산서 이메일 확인 → `BUSINESS`
- 개인: 신분·정산계좌 확인(외부 본인인증은 미연동, 수동 확인) → `INDIVIDUAL`, 원천징수 3.3%
- 계좌 변경 시 `accountChangedAt` 기록 + 본인 알림 발송. 계좌번호는 암호화 저장, 화면에는 마스킹만 노출.

## 3. 분쟁 처리 (`/admin/disputes`)

흐름: **접수 → 지급 보류 확인 → 양측 자료 제출 → 수정·합의 제안 → 판단 → 결과 처리**

1. 접수 시: 주문 `disputeStatus=OPEN`, `payoutStatus=ON_HOLD`, 결제사업자 지급 중지 요청 결과(`providerHoldState`)
   를 **따로** 기록한다. 중지 요청이 실패하면 "미지원/실패"로 표시된다.
2. 자료 제출: 구매자·판매자 모두 `evidence` JSON 배열에 누적된다.
3. 판단(10자 이상 근거 필수):
   - `RESUME` 거래 재개 → 검수 상태로 복귀
   - `REFUND` / `PARTIAL_REFUND` → 환불 접수 생성(금액 지정 가능)
   - `PAYOUT` 지급 진행 → 정산 가능 상태로 전환
4. 판단 즉시 양측에 알림. 이의제기는 고객지원 문의로 접수한다.

**주의**: 분쟁 상태를 바꿨다고 외부 PG 지급이 자동으로 멈추지 않는다. `providerHoldState` 가 실제 결과다.

## 4. 환불 처리 (`/admin/settlements`)

- 구매자 요청은 `REQUESTED` 이며 **아직 돈이 나가지 않았다**.
- 승인 시 서버가 사업자 취소를 호출하고, **성공 응답을 받은 경우에만** `COMPLETED` 로 바뀐다.
- 부분 환불 미지원 수단(계좌이체·가상계좌로 설정된 경우): `UNSUPPORTED` 로 표시되고, 전액 환불 후 재결제 또는
  계좌 송금 등 대체 절차를 안내한다.
- **이미 지급 완료된 거래**: `RECOVERY_REQUIRED` — 일반 보류로 되돌리지 않고 사후 환수 검토 대상으로 분리된다.
  판매자에게 회수 요청 → 미회수 시 채권 관리 절차로 이관.
- 환불 완료 시: 다운로드 링크 전체 회수, 추가 다운로드 차단, 원장에 `REFUND_OUT` 기록.
  **이미 받은 파일은 회수되지 않는다**는 안내가 구매자·판매자에게 함께 발송된다.

## 5. 판매자 지급 (`/admin/settlements`)

지급 전 확인(시스템이 자동 검증, 실패 시 차단):
- 결제 상태 `PAID`
- 납품 `DELIVERED`
- 검수 `APPROVED` 또는 `AUTO_CONFIRMED`
- 분쟁 없음 / 환불 없음
- 원장 잔액 ≥ 지급액
- 동일 주문 기존 지급 없음

지급 처리:
- `REQUESTED` → 사업자 응답 `PAID` → `PAID`
- 응답 불명확(`UNKNOWN`) → `PROCESSING` 유지, **재요청 금지**. `사업자 조회로 확정` 버튼으로 결과를 확정한다.
- 실패 → `FAILED`, 원장 차감을 `ADJUSTMENT` 로 되돌린다.

### 환불·지급 동시 요청
두 작업 모두 주문 행을 `SELECT ... FOR UPDATE` 로 잠근다. 한쪽이 먼저 끝나면 다른 쪽은 상태를 다시 읽고
차단된다. 원장은 `idempotencyKey` 유니크 제약으로 이중 기록을 막는다.

## 6. 대사 (`/admin/reconciliation`)

- 내부 `Payment` ↔ 사업자 상태(`MockPgTx`), 원장 합계 ↔ 주문 금액, 지급 상태를 비교한다.
- 불일치는 `STATUS_MISMATCH`, `AMOUNT_MISMATCH`, `MISSING_EXTERNAL`, `LEDGER_MISMATCH` 로 남는다.
- **자동 수정하지 않는다.** 결제·지급 불일치는 사업자 콘솔에서 사실 확인 후 수동 처리하고, 원장 조정은
  `ADJUSTMENT` 로 남긴다.

## 7. 고객지원 (`/support`)

- 문의 유형: 결제·환불 / 납품·다운로드 / 분쟁·신고 / 정산·세금 / 계정·판매자 심사 / 기타
- 다운로드 문제 1차 확인: 결제 상태 → 환불·분쟁으로 링크 회수 여부 → 링크 만료(10분, 3회)
- 답변은 티켓에 기록한다(추후 메일 발송 연동 필요).

## 8. 사고 대응

| 상황 | 조치 |
| --- | --- |
| 파일 유출 의심 | 해당 상품 `SUSPENDED`, 판매자 중지, 다운로드 링크 회수(`revokeGrants`), 감사 로그 확인 |
| 계좌 변경 사기 의심 | 판매자 정산 보류, 계좌 재인증 요구, 지급 중단 |
| 결제 상태 불일치 | 대사 실행 → 사업자 콘솔 확인 → 내부 상태 수동 보정 + 감사 로그 |
| 저장소 손상 | 볼트 백업 복구 → 주문 상세에서 해시 일치 확인 → 다운로드 재개 |
| 지급 중복 의심 | `Payout`·`LedgerEntry` 에서 해당 주문의 `PAYOUT_OUT` 개수 확인 (1건이어야 정상) |

## 9. 정기 점검 (권장)

- 매일: 미납품(7일 경과), 검수 기한 임박, `PROCESSING` 지급 건
- 매주: 대사 실행, 분쟁 미결 건, `RECOVERY_REQUIRED` 환불
- 매월: 수수료 정책 검토, 환불·분쟁 통계, 감사 로그 이상 패턴
