# 웹 NVR 설계서 (v0.1 · 2026-10-18)

이 문서는 여러 제조사 IP 카메라를 웹브라우저에서 실시간 감시·녹화·검색·재생·내보내기할 수 있는
업무용 웹 NVR의 설계입니다. 1단계 구현은 이 설계를 기준으로 진행되었고, 실제 검증 결과는
`docs/03-검증결과.md`, 남은 항목은 `docs/04-미구현목록.md`에 따로 기록합니다.

용어: **실장비 검증** = 실제 카메라로 시험 / **테스트 환경 검증** = 합성 RTSP 스트림·ONVIF 시뮬레이터로 시험 /
**미검증** = 코드는 있으나 시험 못함 / **미구현** = 코드 없음.

### 1.1 서비스별 책임

| 서비스 | 책임 | 외부 공개 | 인증 연결 | 장애 시 동작 |
|---|---|---|---|---|
| **caddy** | HTTPS 종료, 웹화면 정적 파일, `/api`→api, `/rtc`·`/hls`→mediamtx 프록시 | 443(80은 리다이렉트) | 없음(전달만) | 재시작 시 녹화와 무관 |
| **api** | 로그인·권한, 현장·카메라·사용자 관리, ONVIF/RTSP 등록·시험, 녹화 검색·재생 파일 제공, 내보내기 요청, 감사로그, mediamtx 인증 훅 | 아니오(caddy 경유) | 세션 쿠키(HttpOnly) + CSRF 토큰 | 재시작해도 녹화 계속(별도 서비스) |
| **mediamtx** | 카메라 RTSP를 받아 브라우저에 WebRTC(WHEP)·HLS로 중계. 시청자 수와 무관하게 카메라 연결 1개 | WebRTC 미디어 8189/udp(+tcp) | 모든 시청 요청을 api 인증 훅으로 검증(단기 토큰) | 시청만 중단, 녹화 영향 없음 |
| **recorder** | 카메라별 FFmpeg 프로세스 감독, 재인코딩 없는 구간 녹화, 구간 원자적 확정·DB 인덱스, 단절 감지·지수 백오프 재연결, 재시작 복구 | 아니오 | DB 계정 | 재시작 시 미확정 파일 복구 후 녹화 재개 |
| **analytics** (v0.3) | 규칙이 있는 카메라의 보조 스트림을 FFmpeg 로 받아(초당 2장) CPU 분석, 이벤트·스냅샷 기록. 사람 검출은 YOLOX-s(cv2.dnn) 1개 공유 | 아니오 | DB 계정, 카메라 비밀번호 복호화 | 규칙·기준 영상은 DB·파일, 열린 이벤트는 재시작 시 닫음 |
| **worker** | MP4 내보내기 작업, 보관기간·여유공간 기준 순환 삭제, 만료 처리, mediamtx 경로 설정 생성 | 아니오 | DB 계정 | 작업은 DB 상태로 이어서 처리 |
| **db** | PostgreSQL. 설정·인덱스·작업 큐·감사로그 | 아니오 | 내부망 비밀번호 | 영구 볼륨 |

설계 결정:
- **녹화는 카메라에서 직접**(recorder→카메라), **시청은 mediamtx 경유**. mediamtx가 죽거나 재시작해도 녹화가 끊기지 않습니다.
  카메라당 연결 수는 녹화 1 + 시청(서브 1, 메인 확대 시 1) = 최대 3개로 상한이 정해지며 시청자 수에 비례하지 않습니다.
  (카메라 동시 세션 한도가 2인 장비라면 메인 확대 시청을 막는 설정이 필요합니다 → 미구현 목록)
- **작업 큐는 PostgreSQL**(`SELECT … FOR UPDATE SKIP LOCKED`)로 처리합니다. 1단계 규모에서 Redis는 추가 장애 지점만 늘리므로 사용하지 않습니다.
- **관리 API는 FastAPI(Python)** 를 선택했습니다. FFmpeg·ONVIF(SOAP)·파일 처리 도구가 풍부하고, recorder/worker와 코드(모델·보안 모듈)를 공유할 수 있습니다.
- **mediamtx Control API는 사용하지 않습니다**(api: no). 대신 worker가 경로 설정 파일을 생성하고 mediamtx의 공식 *핫 리로드* 기능으로 반영합니다.
  관리 API 표면을 아예 열지 않기 위한 선택입니다.

모든 요청 목적지를 허용망 검사기로 통과시킵니다.

## 2. 배포·네트워크 구조

### 2.1 기본: 현장 서버 1대
카메라와 같은 사설망(또는 라우팅 가능한 망)에 Linux 서버·미니 PC를 두고 Docker Compose로 설치합니다.
외부 사용자는 공인 도메인 또는 VPN을 통해 HTTPS로 접속합니다.

| 포트 | 프로토콜 | 용도 | 공개 범위 |
|---|---|---|---|
| 443 | TCP | 웹화면·API·WHEP 시그널링·HLS | 사용자 |
| 80 | TCP | HTTPS 리다이렉트 / 인증서 발급(ACME) | 선택 |
| 8189 | UDP (+TCP 선택) | WebRTC 미디어(ICE) | 사용자 |
| 5432, 8000, 8888, 8889 | TCP | db / api / mediamtx HLS / mediamtx WebRTC | **내부 전용(포트 게시 안 함)** |
| 카메라 80/443/554/8554 등 | TCP/UDP | ONVIF·RTSP | 서버 → 카메라 방향만 |

WebRTC 연결 조건:
- `NVR_PUBLIC_HOSTS`(서버 LAN IP, 공인 IP/도메인)를 mediamtx `webrtcAdditionalHosts`에 넣어야 브라우저가 미디어 경로를 찾습니다.
- UDP가 막힌 망은 `webrtcLocalTCPAddress: :8189`(TCP 8189) 또는 TURN(coturn) 설정이 필요합니다. 그래도 안 되면 **HLS 대체 재생**으로 자동 전환합니다(지연 수 초).
- 브라우저의 RTSP 직접 재생은 전제하지 않습니다.

### 2.2 ONVIF 자동 탐색과 Docker 네트워크 제약
- WS-Discovery는 UDP 멀티캐스트(239.255.255.250:3702)라 **같은 L2 브로드캐스트 도메인**에서만 동작합니다. 라우터·VPN을 넘지 못합니다.
- Docker 기본 bridge 네트워크 안의 컨테이너는 멀티캐스트를 현장망으로 내보내지 못합니다. 자동 탐색이 필요하면 탐색 담당 서비스만
  `network_mode: host`로 실행하고, 관리자가 허용한 네트워크 인터페이스로만 송신해야 합니다(2단계).
- 클라우드 서버나 사용자 브라우저가 현장 사설 IP 카메라에 접근할 수 있다고 가정하지 않습니다.
- 자동 탐색이 불가능한 환경을 위해 **IP·포트·서비스 주소 수동 등록**을 1단계부터 제공합니다.

### 2.3 여러 현장 확장 구조 (3단계 설계)
```
 [중앙 웹 NVR] ── 사용자·권한·감사로그·통합 화면·검색 색인(메타데이터)
      ▲  mTLS 아웃바운드 터널(현장→중앙) 또는 WireGuard VPN
 ┌────┴─────┐   ┌──────────┐
 │현장 A Edge│   │현장 B Edge│ … 각 현장: recorder·worker·mediamtx·로컬 저장소 (녹화는 현장에서)
 └──────────┘   └──────────┘
```
- **녹화는 현장에서**: 중앙망이 끊겨도 현장 녹화는 계속됩니다. 중앙은 관리·조회 창구입니다.
- Edge Agent는 현장에서 중앙으로 **나가는 연결만** 맺어(방화벽 개방 불필요) 카메라 탐색·연결 진단·상태를 보고합니다.
- 중앙은 Edge 하트비트가 끊기면 해당 현장을 "네트워크 단절"로 표시하고, 그 현장의 영상을 "확인 불가"로 표시합니다(녹화 중단으로 단정하지 않음).
- 현재 DB에 `sites` 단위가 이미 있어, 현장 단위 권한·허용망·시간대를 그대로 확장합니다.

## 3. 프로토콜·코덱·제조사 지원표

### 3.1 입력 프로토콜 (1단계 기준)

| 항목 | 상태 | 비고 |
|---|---|---|
| ONVIF 수동 등록 (Device·Media·Media2) | 구현 · 테스트 환경 검증(시뮬레이터) · 실장비 미검증 | WS-UsernameToken Digest, 시간오차 보정, HTTP Digest 재시도 |
| RTSP 수동 등록 | 구현 · 테스트 환경 검증 | 사용자 정의 경로 허용 |
| RTSP over TCP / UDP 선택 | 구현 · TCP 테스트 환경 검증, UDP 미검증 | 기본 TCP(손실·NAT에 강함) |
| RTSPS | 구현(FFmpeg 지원) · 미검증 | 인증서 검증 예외는 장치별 승인 필요 |
| HTTP/HTTPS 스냅샷 (ONVIF GetSnapshotUri) | 구현 · 테스트 환경 검증 | 없으면 RTSP 1프레임 추출 |
| MJPEG 입력 | 미구현 | 브라우저 WebRTC 재생·MP4 녹화 호환성 별도 설계 필요 |
| RTMP·SRT 입력 | 미구현(확장 검토) | mediamtx는 지원하나 사용 사례 확인 후 |
| ONVIF 자동 탐색(WS-Discovery) | 미구현(2단계) | 2.2 제약 참조 |

### 3.2 코덱 (프로토콜과 분리 관리)

| 코덱 | 녹화(원본 복사) | 브라우저 실시간(WebRTC) | 녹화 재생(MP4) | 처리 |
|---|---|---|---|---|
| H.264 (B-프레임 없음) | ○ | ○ | ○ | 웹 시청은 H.264 서브 스트림 우선 |
| H.264 (B-프레임 포함) | ○ | × (WebRTC 규격 외) | ○ | 카메라 설정에서 B-프레임 끄기 권장 |
| H.265/HEVC | ○ (hvc1 태그) | 제한적: Chrome은 Windows+지원 GPU에서만, Safari는 지원 | 브라우저 하드웨어 디코더에 의존 | UI에 경고 표시, 서브 스트림을 H.264로 설정 권장 |
| AAC | ○ | × (WebRTC는 Opus/G.711) | ○ | 실시간 음성은 2단계(Opus 변환 필요) |
| G.711 (PCMU/PCMA) | AAC로 변환 저장(음성만, 영상은 원본) | ○ (mediamtx 지원) | ○ (AAC) | MP4 컨테이너 호환 때문 |
| MJPEG | × | × | × | 미구현 |

mediamtx는 코덱을 자동 변환하지 않습니다(공식 문서: 호환성을 위해 FFmpeg로 H.264 baseline + Opus 재인코딩 예시 제시).
본 시스템은 **녹화 원본은 그대로**, 시청용 변환이 필요한 경우에만 별도 변환 경로를 둡니다(2단계, 서버 CPU 산정 필요).

### 3.3 ONVIF 프로파일

| 프로파일 | 용도 | 본 시스템 |
|---|---|---|
| T | 고급 영상 스트리밍(H.264/H.265, Media2, 이벤트) | 중심. Media2 우선 조회, 없으면 Media(ver10) |
| S | 기본 영상 스트리밍(기존 장비) | 호환용(Media ver10) |
| G | 장치 내 녹화 저장·검색·재생 | 3단계 |
| M | 메타데이터·분석 이벤트 | 3단계 |

ONVIF **연동 구현**과 **공식 적합성 인증(Conformant)** 은 다릅니다. 공식 적합성은 ONVIF 적합 제품 목록에 등재된 제품만 해당하며,
본 시스템은 적합성 인증을 받은 제품이 아닙니다. UI에서도 "ONVIF 연동"으로만 표기합니다.

## 8. 녹화 엔진 설계

- 카메라별 FFmpeg 1개: `-rtsp_transport tcp|udp -timeout 10s -i <URL> -map 0:v:0 -map 0:a:0? -c:v copy` →
  `segment` 먹서, 시계 경계 정렬(`-segment_atclocktime`) 60초 구간, 조각화 MP4(`frag_keyframe+empty_moov`)로 **비정상 종료에도 마지막 조각까지 복구 가능**.
- 구간 확정: FFmpeg 구간 목록(CSV)에 구간이 닫히면 → `ffprobe` 검증 → `+faststart` MP4로 재다중화(복사, 재인코딩 없음) → 임시 이름에 쓰고
  `fsync` 후 `rename`(원자적) → DB 인덱스 삽입 → 작업 파일 삭제. 진행 중인 파일은 `incoming/` 에만 있으므로 정리 작업이 건드리지 않습니다.
- 시각: 서버 시계(UTC, NTP 필수) 기준. 시계 경계로 잘린 구간 파일명 시각과 구간 PTS로 기준점을 잡아 각 구간 시작·끝을 계산합니다(오차 ±1~2초, GOP 의존).
  카메라 시계는 녹화 시각에 쓰지 않으며, ONVIF 조회 시 오차만 진단·표시합니다.
- 단절: FFmpeg 종료 원인(stderr)을 인증 실패 / 연결 거부·시간 초과 / 스트림 없음(404) / 코덱 미지원 / 디스크 쓰기 실패로 분류,
  카메라 상태·이벤트에 기록하고 지수 백오프(2→60초, 인증 실패는 60→600초: 카메라 계정 잠금 방지)로 재연결합니다. 누락 구간은 인덱스 공백으로 드러납니다.
- 복구: recorder 시작 시 `incoming/`의 잔여 파일을 복구·확정하고, 저장소에는 있으나 DB에 없는 파일은 파일명(카메라·시작시각·길이)으로 재색인합니다.
- 음성: AAC는 복사, G.711은 MP4 호환을 위해 AAC로 변환(영상은 항상 원본 복사).
- 보관: worker가 1분마다 (a) 카메라별 보관일 초과 구간, (b) 여유 공간이 기준 미만이면 가장 오래된 비보호 구간부터 삭제.
  삭제는 `status=deleting` 표시 → 파일 삭제 → 행 삭제 순서로 처리해 중간에 죽어도 다시 이어서 정리합니다. 보호 구간은 삭제하지 않습니다.
  모두 보호되어 공간을 만들 수 없으면 "저장공간 부족(위험)" 이벤트를 남깁니다.
- 이벤트 전 녹화(2단계): 상시 수신 중인 구간 파일을 링 버퍼로 사용(최근 N개 구간을 이벤트 전까지 "임시"로 유지, 디스크 상한 설정).

## 9. 보안 설계 요약

- 비밀번호: argon2id. 카메라 비밀번호: Fernet(AES-128-CBC+HMAC) 암호화, **마스터 키는 DB가 아닌 Docker secret 파일**(`secrets/master.key`).
- 로그·URL·API 응답: 스트림 주소는 인증정보를 뺀 형태로만 저장·응답. FFmpeg 출력은 `://사용자:암호@` 와 암호 문자열을 가려서 기록.
- 세션: 무작위 256비트 토큰(HttpOnly·Secure·SameSite=Strict 쿠키), DB에는 해시만. 유휴/절대 만료, 강제 로그아웃. 변경 요청은 CSRF 토큰 필수.
- 로그인 제한: 계정 15분 내 5회 실패 시 15분 잠금, IP 15분 내 20회 실패 시 차단.
- 미디어 접근: 녹화 파일은 요청마다 세션·카메라 권한 검증. 실시간은 HMAC 서명 단기 토큰을 mediamtx가 api 훅으로 검증(경로·만료·세션 유효성).
  mediamtx 경로 이름을 알아도 토큰 없이는 시청 불가.
- SSRF: 카메라 주소는 DNS 해석 후 **현장 허용망(CIDR)** 안에 있어야 하고, 루프백·링크로컬(169.254.0.0/16 메타데이터 포함)·멀티캐스트·
  NVR 내부 Docker 망은 항상 차단. 해석된 IP로 고정 연결(재해석 우회 방지). HTTP 리다이렉트는 따라가지 않고 목적지 재검증 후 최대 2회만 허용.
  ONVIF가 알려주는 XAddr·스트림 URI도 같은 검사를 통과해야 사용.
- FFmpeg: 셸을 쓰지 않고 인자 배열로 실행, URL은 `rtsp://`/`rtsps://`만 허용·제어문자 차단, `-protocol_whitelist` 제한, 출력 경로는 서버가 정수 ID로만 생성.
- 인증서 검증 예외: 카메라별 `tls_insecure`는 최고관리자만 켤 수 있고 승인자·시각과 감사로그가 남습니다.

## 10. 성능·용량 산정 원칙
채널 수만으로 성능을 약속하지 않습니다. 다음을 함께 산정합니다.
- 저장: `비트레이트(Mbps) × 3600 ÷ 8 × 녹화시간(h/일) × 보관일 × 카메라 수` + 음성(약 64kbps) + 컨테이너 부가정보(약 1~2%) + 운영 여유(기본 15%).
  화면의 용량 산정기는 이를 **추정치**로 표시하고, 저장장치 화면의 카메라별 실측 사용량과 구분합니다.
- CPU: 재인코딩 없는 녹화는 카메라당 부하가 낮지만, 구간 확정 시 재다중화로 디스크 쓰기가 약 2배가 됩니다. 정확 내보내기·워터마크·시청용 변환은 CPU를 크게 사용합니다.
- 디스크: 지속 쓰기 대역폭 ≥ 총 입력 비트레이트 × 2.5(재다중화·내보내기 여유). HDD는 NVR/감시용 등급 권장, SSD 캐시 불필요.
- 네트워크: 서버 입력 = Σ(녹화 메인 스트림) + Σ(시청 중 서브/메인), 출력 = 시청자 수 × 시청 스트림 비트레이트.

## 11. 1단계 완료 기준
1. `docker compose up -d` 와 초기 관리자 생성 명령만으로 설치된다.
2. 로그인/로그아웃·세션 만료·로그인 제한·역할별 접근 차단이 동작한다.
3. 현장(허용망 포함)·카메라를 등록·수정·비활성화·삭제할 수 있고 녹화 삭제는 별도 동작이다.
4. ONVIF(장치정보·프로파일·스트림 URI·스냅샷 URI) 및 RTSP 수동 등록과 연결 시험이 동작하고 실패 원인이 구분된다.
5. 브라우저 1·4분할 실시간 보기(WebRTC, 실패 시 HLS)가 권한 토큰으로만 열린다.
6. 브라우저를 닫아도 서버 연속 녹화가 계속되고, 서비스 재시작 후 설정·영상이 유지되며 녹화가 자동 재개된다.
7. 카메라 단절 시 누락 구간이 기록되고 복구 후 자동 재연결된다.
8. 날짜·시간으로 검색하고 재생(배속 포함)할 수 있다.
9. 지정 구간 MP4 내보내기가 백그라운드로 처리되고 다운로드 파일이 일반 플레이어에서 재생된다.
10. 권한 없는 사용자는 API·녹화 파일·실시간 스트림·다운로드 모두 차단된다.
11. 카메라 비밀번호가 로그·API 응답에 노출되지 않는다.
12. 위 항목별 검증 결과가 "합성 스트림 / 자동화 / 실장비"로 구분되어 기록된다.
