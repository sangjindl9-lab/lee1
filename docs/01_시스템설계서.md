# SS-ERP 시스템 설계서

전기·정보통신·건축공사 전문 통합 회계 ERP (회사별 설치형)

| 항목 | 내용 |
|---|---|
| 문서 버전 | 1.0 (1단계 착수 기준) |
| 작성일 | 2026-10-21 |
| 배포 형태 | 회사별 설치형 (고객사 서버 또는 고객사 전용 클라우드에 단독 설치, 라이선스 키로 활성화) |
| 대상 | 전기·통신·건축 전문건설업체 (직원 5~200명 규모) |

---

## 1. 업무분석

### 1.1 핵심 문제

전문건설업체는 현장 단위로 돈이 움직이지만, 대부분의 범용 회계 프로그램은 회사 단위로 장부를 본다. 그래서 실무에서는 다음이 따로 논다.

- 공무팀의 계약·실행예산 엑셀
- 구매담당의 발주서 엑셀·종이
- 경리의 세금계산서·통장 내역
- 세무사 사무실의 회계 장부

결과적으로 "이 현장 지금 남는 거야?"라는 대표의 질문에 즉시 답할 수 없다. SS-ERP의 존재 이유는 **모든 돈의 흐름에 현장 번호를 붙여, 현장 손익을 실시간으로 보이게 하는 것**이다.

### 1.2 돈의 흐름 모델 (금액의 5단계)

같은 "금액"이라도 단계가 다르면 의미가 다르다. 시스템 전체에서 아래 단계를 절대 섞지 않는다.

| 단계 | 매출 측 (받을 돈) | 원가 측 (줄 돈) |
|---|---|---|
| ① 계획 | 계약금액 | 실행예산 |
| ② 확정 | 변경계약 승인 | 발주확정 / 하도급계약 |
| ③ 발생 | 기성청구 승인 → 매출인식 | 검수완료 → 발생원가 |
| ④ 증빙 | 매출세금계산서 발행 | 매입세금계산서 수취 |
| ⑤ 현금 | 수금 | 지급 |

- 미수금 = ③매출인식 − ⑤수금 (세금계산서 기준 채권은 별도 표시)
- 미지급금 = ③발생원가 − ⑤지급
- 세금계산서를 받았다는 사실(④)은 지급(⑤)을 의미하지 않는다.
- 매입 부가세(공제 가능분)는 원가에 넣지 않고 부가세대급금으로 분리한다.
- 계약보증금·선급금·유보금은 각각 독립 계정으로 관리한다.

### 1.3 업무 주체와 하는 일

| 역할 | 주요 업무 | 데이터 범위 |
|---|---|---|
| 최고관리자 | 시스템 설정, 사용자·권한, 연동 설정, 백업 | 전체 |
| 대표이사 | 전 현장 손익·자금 조회, 최종 결재 | 소속 회사 전체 |
| 임원 | 지정 회사·현장 조회, 결재 | 지정 범위 |
| 회계관리자 | 전표 승인, 마감, 세금계산서, 자금 | 소속 회사 전체 |
| 경리담당자 | 증빙 등록, 전표 작성, 지급결의 | 소속 회사 전체(승인권 없음) |
| 공무담당자 | 계약, 변경계약, 실행예산, 기성 | 담당 현장 |
| 구매담당자 | 거래처, 자재, 발주, 검수 | 소속 회사 전체 |
| 현장소장 | 담당 현장 발주요청·지출·노무 | 배정된 현장만 |

| 외부 세무담당자 | 승인·확정된 회계자료 열람 | 소속 회사, 확정 자료만 |

### 3.1 구성도

```
[브라우저 PC·태블릿·모바일]

        ▼
[리버스 프록시 Caddy]  ── 자동 TLS 인증서, 보안 헤더
```

## 4. 데이터베이스 설계

### 4.1 공통 규칙

- 모든 업무 테이블은 `companyId`를 가진다. 모든 조회는 서버의 범위 필터를 반드시 통과한다.
- 기본키는 UUID(`uuid v7` 대신 PostgreSQL `gen_random_uuid()`), 사람이 읽는 번호(공사관리번호, 전표번호)는 별도 컬럼 + 회사별 고유 제약.
- 사람이 읽는 번호는 `NumberSequence` 테이블에서 행 잠금(`SELECT … FOR UPDATE`)으로 발급 → 동시 등록에도 중복 없음.
- 금액 `numeric(18,2)`, 수량 `numeric(18,4)`, 단가 `numeric(18,4)`, 비율 `numeric(7,4)`.
- 재무 거래는 삭제하지 않는다. 상태(`DRAFT → SUBMITTED → APPROVED → CANCELLED`)와 역분개로만 바꾼다.
- 기준정보(거래처·자재)는 소프트 삭제(`deletedAt`).
- 모든 테이블에 `createdAt`, `createdById`, `updatedAt`, `updatedById`.
- 낙관적 잠금 `version` 컬럼: 동시 수정 시 늦은 쪽은 "다른 사용자가 먼저 수정했습니다" 오류.

### 4.2 엔터티 관계 (전체)

```
Company 1─┬─N Membership N─1 User ─N UserSession
          │       └─N MembershipRole N─1 Role ─N RolePermission
          │       └─N ProjectAssignment N─1 Project
          ├─N Project ─┬─1 Contract ─N ContractRevision
          │            ├─N ProjectBudget N─1 CostCode
          │            ├─N PurchaseOrder ─N PurchaseOrderLine N─1 Material
          │            │        └─N GoodsReceipt ─N GoodsReceiptLine
          │            ├─N ProgressClaim
          │            ├─N Subcontract ─N SubcontractClaim
          │            ├─N LaborRecord
          │            └─N JournalLine (현장 보조원장 키)
          ├─N Vendor ─N VendorPrice N─1 Material
          ├─N TaxInvoice ─N TaxInvoiceLine
          │        └─N TaxInvoiceMatch ─▶ PurchaseOrder / GoodsReceipt / ProgressClaim
          ├─N PaymentRequest ─N Payment ─▶ BankTransaction
          ├─N BankAccount ─N BankTransaction
          ├─N JournalEntry ─N JournalLine N─1 Account
          ├─N Approval ─N ApprovalStep  (대상: 문서종류 + 문서ID)
          ├─N Document ─N DocumentExtraction
          ├─N IntegrationConfig / ApiCredential
          └─N AuditLog (해시 체인)
```

### 4.3 1단계 구현 테이블

`Company, User, UserSession, Membership, Role, RolePermission, MembershipRole, ProjectAssignment, Project, Vendor, FileObject, NumberSequence, AuditLog, SystemSetting, TaxRateSetting, LicenseState`

2단계 이후 테이블은 해당 단계에서 마이그레이션으로 추가한다 (빈 테이블을 미리 만들어 "있는 척"하지 않는다).

### 4.4 무결성 장치

| 위험 | 장치 |
|---|---|
| 번호 중복 | `@@unique([companyId, code])` + 시퀀스 행 잠금 |
| 중복 분개·지급 | 원천문서별 `@@unique([sourceType, sourceId, purpose])` (2단계) |
| 차대 불일치 | 서비스 검증 + DB 지연 제약 트리거로 이중 차단 (2단계) |
| 감사로그 변조 | `UPDATE/DELETE` 차단 트리거 + 이전 행 해시를 포함한 SHA-256 체인 |
| 마감기간 수정 | `AccountingPeriod.locked` 검사 트리거 (2단계) |
| 동시 승인 | `version` 조건부 업데이트, 영향 행 0이면 거부 |

## 5. 권한·보안 설계

### 5.1 권한 모델

권한은 `리소스 : 동작` 쌍이다.

- 리소스: `dashboard, project, contract, budget, vendor, material, purchase, receipt, taxinvoice, expense, payment, journal, approval, report, document, labor, user, role, company, audit, integration, apikey, license, backup`
- 동작: `read, create, update, delete, approve, export, api`

역할은 권한 묶음 + **데이터 범위**를 가진다.

| 범위 | 의미 |
|---|---|
| `COMPANY` | 소속 회사의 모든 현장 |
| `ASSIGNED` | `ProjectAssignment`로 배정된 현장만 |
| `CONFIRMED_ONLY` | 승인·확정 상태 자료만 (외부 세무담당자) |

한 사용자가 여러 회사에 소속될 수 있고, 회사마다 다른 역할을 가질 수 있다. 여러 역할의 권한은 합집합, 데이터 범위는 가장 넓은 것을 적용한다.

판정 순서 (모든 API 요청):
1. 인증 (세션 유효, 비활성·잠금 계정 차단)
2. 회사 컨텍스트 (`X-Company-Id` 헤더 → 소속 여부 확인, 아니면 404)
3. 기능 권한 (`@RequirePermission('project','update')`)
4. 데이터 범위 (서비스 계층에서 `where` 조건 강제 주입)

권한 없는 다른 회사·현장 자료는 **403이 아니라 404**로 응답해 존재 여부도 노출하지 않는다.

### 5.2 인증

- Argon2id (메모리 64MB, 반복 3) 비밀번호 해시
- 비밀번호 정책: 10자 이상, 영문·숫자·특수문자 중 3종, 아이디·회사명 포함 금지
- 로그인 5회 연속 실패 시 15분 잠금, 실패 응답은 "아이디 또는 비밀번호가 올바르지 않습니다"로 통일 (계정 존재 여부 비노출)
- 세션: 무작위 256비트 토큰, DB에는 SHA-256 해시만 저장, `HttpOnly; Secure; SameSite=Strict` 쿠키
- 유휴 30분, 절대 12시간 만료. 비밀번호 변경·관리자 강제 로그아웃 시 전 세션 폐기
- CSRF: 이중 제출 토큰 (`csrf` 쿠키 + `X-CSRF-Token` 헤더 일치 검사) — 상태 변경 요청 전체
- 2단계 인증(TOTP, Google Authenticator 등): 1단계에서 구현, 역할별 필수화 설정 가능

### 5.3 데이터 보호

| 대상 | 처리 |
|---|---|
| 거래처 계좌번호, 주민등록번호(노무) | AES-256-GCM 필드 암호화, 키는 환경변수, 화면에는 마스킹(`110-***-***789`) |
| API 키·연동 비밀번호 | 동일 암호화, 저장 후 재조회 불가(마지막 4자리만) |
| 업로드 파일 | 확장자 + 실제 파일 서명(매직바이트) 이중 검사, 20MB 제한, 저장명 무작위화, 실행파일·스크립트 차단 |
| 전송 | HTTPS 필수, HSTS |
| 헤더 | Helmet (CSP, X-Frame-Options DENY, nosniff, Referrer-Policy) |
| 속도 제한 | 로그인 분당 10회/IP, 일반 API 분당 300회/사용자 |
| 로그 | 비밀번호·토큰·계좌번호 자동 마스킹 |

### 5.4 감사로그

누가, 언제, 어디서(IP·브라우저), 무엇을(리소스·ID), 어떻게(변경 전·후 값)를 기록한다. 각 행은 `hash = SHA256(prevHash + 내용)`으로 연결되어, 중간 한 줄이라도 고치면 이후 검증이 모두 깨진다. 관리 화면에 "무결성 검사" 버튼을 둔다.

### 5.5 라이선스 (설치형 판매)

- 판매자가 Ed25519 개인키로 라이선스 파일에 서명 (회사명, 사업자번호, 최대 사용자 수, 만료일, 허용 모듈)
- 프로그램에는 공개키만 내장 → 고객이 내용을 고치면 서명 검증 실패
- 인터넷 연결 없이 검증 (폐쇄망 설치 가능)
- 만료 시 조회만 허용(읽기 전용 모드), 데이터는 절대 잠그지 않음
- 발급기(`tools/license`)는 고객 배포본에 포함하지 않는다

## 6. UI/UX 설계

### 6.1 화면 원칙

1. **현장이 먼저다.** 상단 바에 지금 보고 있는 회사·현장이 항상 보인다. 현장을 바꾸면 모든 화면이 그 현장 기준으로 바뀐다.
2. **숫자는 장부처럼.** 금액은 우측 정렬, 고정폭 숫자, 천 단위 구분. 음수는 한국 장부 관례대로 빨간 `△1,250,000`.
3. **공급가액·부가세·합계는 항상 셋이 같이.** 금액 입력 화면은 세 칸이 한 묶음이며 서버가 다시 계산해 검증한다.
4. **표가 주인공.** 업무 화면은 카드 나열이 아니라 데이터 표. 행 높이 36px, 헤더 고정, 하단 합계행 고정.
5. **상태는 색 + 글자.** 색만으로 구분하지 않는다 (색약 사용자 고려).
6. **위험한 동작은 두 번.** 실제 발행·송금·마감은 확인 대화상자에 대상·금액을 다시 보여주고 "운영" 표시를 붙인다. 테스트 모드는 화면 상단 전체에 노란 띠.
7. **키보드로 일할 수 있게.** `/` 통합검색, `Ctrl+S` 저장, 표 안 방향키 이동, `Esc` 닫기.

### 6.2 디자인 토큰

**색상** — 전기 배선 색상 규격에서 착안한 공종 색과, 결재 인주색을 핵심 정체성으로 사용한다.

| 이름 | 라이트 | 다크 | 용도 |
|---|---|---|---|
| 먹(ink) | `#17202B` | `#E6EAF0` | 본문, 숫자 |
| 지면(paper) | `#F5F6F8` | `#0F141A` | 앱 배경 |
| 면(surface) | `#FFFFFF` | `#171D25` | 패널, 표 |
| 선(line) | `#DDE1E7` | `#2A323D` | 구분선 |
| 강철(steel) | `#2B4C6F` | `#7FA6CF` | 주요 버튼, 선택 상태 |
| 인주(seal) | `#C42B1C` | `#F0705F` | 결재 도장, 반려, 음수 금액 |
| 전기(공종) | `#B7791F` | `#C4862A` | 공종 표식 |
| 통신(공종) | `#2563B0` | `#4F8CD6` | 공종 표식 |
| 건축(공종) | `#2F8A4A` | `#43A35F` | 공종 표식 |
| 복합(공종) | `#7A4FB5` | `#9B74DC` | 공종 표식 |

공종 4색은 색약(적록·청황) 시뮬레이션 구분도, 일반 시력 구분도, 배경 대비 3:1 검사를 밝은·어두운 모드 모두 통과한 값입니다. 색만으로 구분하지 않도록 항상 공종 이름을 함께 씁니다.

좌측 메뉴는 짙은 강철 남색 `#16202C`로 화면과 분리한다.

**글꼴** — IBM Plex Sans KR (엔지니어링 회사의 기술 문서 느낌, 숫자 가독성 우수). 폐쇄망 설치를 위해 웹폰트를 프로그램에 내장한다. 숫자는 `tabular-nums`.

| 단계 | 크기/행간 | 용도 |
|---|---|---|
| 화면 제목 | 20 / 28, 600 | 페이지 제목 |
| 구역 제목 | 15 / 22, 600 | 패널 제목 |
| 본문 | 13 / 20, 400 | 표·폼 (ERP 밀도 기준) |
| 보조 | 12 / 16, 400 | 도움말, 메타 |
| 핵심 숫자 | 22 / 28, 600, tabular | 대시보드 지표 |

**간격** 4px 기준(4·8·12·16·24·32). **모서리** 입력·버튼 4px, 패널 6px, 도장은 원형.

### 6.3 기억에 남는 한 가지: 결재 도장

결재가 필요한 모든 문서 우측 상단에 실제 종이 결재란처럼 `담당 | 검토 | 승인` 칸을 두고, 승인된 칸에는 인주색 원형 도장(이름·날짜)이 찍힌다. 반려는 사선 도장. 출력물(PDF)에도 동일하게 찍힌다. 나머지 화면 요소는 조용하고 절제되게 유지해 이 도장이 돋보이게 한다.

## 7. 구현 우선순위

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 1 | 기반: 로그인·MFA·권한·회사·현장·거래처·대시보드·감사로그·라이선스·Docker | 권한 격리 테스트 통과, 실제 DB 저장·조회·수정·삭제 |
| 2 | 회계·발주 핵심: 자재, 구매요청·발주·검수, 전자결재, 지급결의, 복식부기, 현장원가 | 시나리오 A(세금계산서 제외)·E(은행 제외) 통과 |
| 3 | 세금계산서·스캔: 팝빌/바로빌 어댑터(Sandbox), 홈택스 수집, OCR 어댑터, 대사 | 시나리오 B 통과, 테스트/운영 모드 분리 테스트 |
| 4 | 공사관리 고도화: 변경계약, 기성, 수금, 하도급, 노무, 준공정산 | 시나리오 C·D 통과 |
| 5 | 금융·외부 API·운영: 은행·카드(엑셀 업로드 우선), 나라장터, 공개 REST API, 백업 화면 | 시나리오 A~E 전체 통과, 운영 배포 |

외부 연동(팝빌·바로빌·금융·OCR)은 고객사가 각 업체와 계약해 발급받은 키가 있어야 실제 동작한다. 키가 없으면 화면에 "미연동"으로 표시하며, 어떤 경우에도 가짜 결과를 실제처럼 보여주지 않는다.
