# 4. 운영자 처리 매뉴얼

운영 화면은 `/admin` 이다. 들어갈 때 비밀번호를 한 번 더 확인하며(30분 유지), 모든 처리는 감사 기록 탭에 남는다.

## 권한

| 권한 | 할 수 있는 일 |
| --- | --- |
| 심사 | 판매자 승인·정지, 상품·파일 심사, 지식재산권 등록 심사, 신고 처리 |
| 고객지원 | 분쟁 결정, 검수 종료 심사, 신고 처리, 문의 답변, 계약서 법률 검토 완료 표시 |
| 정산 | 계좌 확인, 직권 환불, 판매자 지급 요청·조회, 수수료 정책, 운영 정책, 대사 |
| 최고관리자 | 위 전부, 운영자 권한 부여, 결제 사업자 기능 확인표 기록 |

## 날마다 볼 것 (심사·대기 탭)

1. **판매자 심사와 계좌 확인.** 계좌를 바꾼 판매자는 다시 확인할 때까지 지급이 막힌다. 본인이 바꾼 것인지 확인한 뒤 "계좌 확인 완료"를 누른다.
2. **상품·파일 심사.** 파일별 세 가지 검사 결과를 본다. "문제 발견"이 있으면 제출 자체가 막히므로 여기에는 올라오지 않는다. "검사 불가"는 검사하지 못했다는 뜻이다. 심사는 품질이나 권리를 보증하는 절차가 아니다.
3. **미납품·검수 지연.** 전달 실패 주문은 저장소 상태를 확인하고 "납품 다시 확인"을 누른다. 복구되면 그때부터 검수 기간이 시작된다. 복구할 수 없으면 거래 탭에서 직권 환불한다.
4. **검수 종료 심사 요청.** 기한이 지났고, 구매자가 확정도 문제 제기도 하지 않았고, 다운로드 기록이 있는지 본 뒤 근거를 적고 결정한다.
5. **신고.** "신규 판매 제한"을 누르면 상품이 내려가고, 같은 상품의 결제된 주문 수가 표시된다. 거래 탭에서 해당 주문들을 확인해 구매자에게 안내한다.

## 분쟁 처리 (분쟁 탭)

1. 거래 작업실에서 양측이 낸 의견·증빙·수정 제안·합의 제안을 읽는다.
2. 주문에 고정된 검수 기준과 제공 범위를 기준으로 판단한다. 계약에 없는 기능 요구는 변경 계약 대상이다.
3. 결정을 고르고 근거를 적는다. 근거 없이는 저장되지 않는다.
   - 거래 재개: 판매자가 보완하기로 했을 때. 검수 기간이 다시 시작된다.
   - 정산 진행: 계약 기준을 충족했을 때.
   - 전액·부분 환불: 결제 사업자의 취소 성공을 확인한 뒤에만 완료로 바뀐다.
   - 외부 해결 절차 안내: 플랫폼이 판단하기 어려운 권리 분쟁 등. 내부 정산 보류는 유지된다.
4. 양측에 결과와 이의제기 방법(7일)이 자동으로 안내된다.

분쟁 화면의 "사업자 지급 보류" 값은 결제 사업자에서 실제로 일어난 결과다. `unsupported` 나 `failed` 면 플랫폼 내부 보류만 걸려 있는 것이므로, 사업자 관리 화면에서 지급 일정을 직접 확인한다.

**부분 환불 미지원 결제수단.** 환불이 "부분 환불 미지원"으로 남는다. 양측과 협의해 전액 환불 후 합의 금액으로 재결제하거나 합의로 종결하고, 거래 탭에서 직권 환불(전액)로 처리한다.

**이미 지급된 거래.** 환불이 "사후 환불·회수 검토"로 남는다. 자동 처리는 없다. 판매자와 회수 방법을 협의하고 결과를 분쟁 기록에 남긴다.

## 환불과 정산 (거래 탭 → 주문, 환불·정산 탭)

- **지급 요청**은 결제 완료, 사업자 상태 일치, 납품, 검수 종료, 분쟁 없음, 환불 진행 없음, 판매자 승인·계좌 확인, 미지급, 잔액을 모두 확인한 뒤에만 접수된다. 막히면 사유가 모두 표시된다.
- "지급 요청 접수"는 완료가 아니다. 사업자의 지급 완료를 확인한 뒤 "지급 완료"가 된다.
- 응답이 불명확하면 "지급 결과 확인 중"이 된다. 1분마다 같은 멱등성 키로 조회하고, 사업자에 접수 기록이 없을 때만 같은 키로 다시 요청한다. 수동으로는 "지급 결과 조회"를 누른다. 새 지급을 따로 만들지 않는다.
- **직권 환불**은 금액과 근거를 적는다. 결제 취소 응답이 불명확하면 "결제 취소 처리 중"으로 남고, 조회로 확인되면 완료된다.

## 대사 (대사 탭)

"지금 대사 실행"을 누르면 모든 결제·지급을 사업자 조회 결과와 비교한다. 불일치 종류:

| 항목 | 뜻 | 조치 |
| --- | --- | --- |
| payment_status | 내부와 사업자의 결제 상태가 다름 | 주문 화면에서 상태 재확인. 사업자에서만 취소된 경우 원인 확인 |
| refund_amount | 환불 누계가 다름 | 사업자 관리 화면의 취소 내역과 환불 기록 대조 |
| payout_status / payout_amount | 지급 상태·금액이 다름 | "지급 결과 조회" 후에도 다르면 지급 중지하고 원인 확인 |
| missing_external | 사업자에 기록이 없음 | 결제 생성 실패 여부 확인 |

불일치가 있는 주문은 지급 요청 단계에서도 막힌다.

## 장애 복구

- 주기 작업이 1분마다 결제 대기 주문 조회, 납품 복구, 환불·지급 결과 확인, 검수 기한 알림을 한다. 심사·대기 탭 아래의 버튼으로 바로 실행할 수도 있다.
- 웹훅이 유실되어도 주기 작업의 조회로 따라잡는다. 웹훅은 서명 검증 후 이벤트 번호로 중복을 걸러 저장한다.
- 백업 대상은 PostgreSQL 전체와 납품물 저장소, 그리고 `FILE_MASTER_KEY` 다. 이 키를 잃으면 보관한 파일을 복호화할 수 없다. DB와 저장소는 같은 시점으로 복구한다.

## 하지 않는 것

- 구매자 시스템에 접속하거나 판매된 프로그램을 원격으로 멈추거나 지우지 않는다.
- 분쟁과 환불의 최종 판단을 자동화나 AI에 맡기지 않는다.
- 사업자에서 확인되지 않은 보호·보류·지급을 완료된 것처럼 안내하지 않는다.
